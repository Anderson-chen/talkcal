# 程式碼註解規則

註解只寫讀現在的程式碼看不出來的事。要不要留，問一句：刪掉之後，接手的人會不會把這段改錯？會才留。

## 寫什麼

- 為什麼這樣寫、換成看起來更直覺的寫法會壞在哪、外部的限制（框架的行為、模型的毛病）。
- 參數念一遍、方法名稱的白話不寫；改個名字就不用解釋的，改名字。
- 只寫這段程式碼本身的事。誰呼叫它、誰接住它丟的例外、port 有哪些 adapter、issue 編號，這些會變，註解不會跟著變。
- 「不再」「刻意」這類字照 `writing.md` 的「不帶進對話的語氣」。

## 一個理由放一個地方

照理由管到多大放，其他地方寫「見 X」，不重寫一遍：

| 理由管到 | 放哪 |
|---|---|
| 一行、一個方法 | 那裡的註解 |
| 整個 class | class 的 Javadoc |
| 一個設定值 | 設定它的檔案（`application.properties`、compose 檔）那個 key 旁邊 |
| 一張表、一個欄位 | 建它的 migration |
| 整個資料夾 | 那個資料夾的 README |

「跟 X 一樣」只是類比，X 拿掉理由就斷了：理由直接寫，或「見」寫理由的那一處。
每個 port 自己的契約（失敗時丟什麼）各寫各的，不算重複。

## 決策的經過不寫進註解

註解寫現在還成立的理由；經過放 commit、PR，引進或換掉技術元件的經過放 ADR（照 `docs/adr/README.md`）。

- 把經過改成條件句，留下壞掉的那個情況：「原本寫成 A，模型就……」改成「寫成 A 的話，模型會……」。
- 以前怎麼做、試了幾次、哪天發現的，拿掉。ADR 有連到這個檔案的（`git grep <檔名> docs/adr`），拿掉前先看 ADR 寫到了沒；沒寫到的寫進這次的 PR 描述，ADR 選好就不改。

## 改程式碼時

- 改了行為、改名或刪掉，用 `git grep` 找提到它的註解（類別名稱、方法名稱、設定 key），說錯的、「見」不到的一起改。
- 跟這次改動無關的註解不順手改寫；要清就另開一個 `docs` commit。

用字、排版照 `writing.md`。
