# 寫作規則（文件、程式碼註解、issue、PR、commit）

寫給一起維護的人看，他們不一定讀過這段程式碼。排版照[中文文案排版指北](https://github.com/sparanoid/chinese-copywriting-guidelines)，
標點照教育部《重訂標點符號手冊》，句子避開 [Humanizer-zh](https://github.com/op7418/Humanizer-zh) 列的 AI 寫作痕跡。

## 排版

- 中文和英文、數字之間加一個空格：`app 在 8090`。
- 數字和單位之間加空格：`500 MB`、`15 分鐘`；百分比和度數不加：`10%`。
- 全形標點旁邊不加空格。
- 中文句子用全形標點，引號用「」，書名號用《》；英文句子和專有名詞裡用半形。
- 數字一律半形。標點不要連用（`！！`、`？！`）。
- 專有名詞照官方大小寫：GitHub、PostgreSQL、Next.js，不寫 Github、postgres（指程式名稱、指令時例外，放進 `code`）。

## 用語

中文技術社群習慣直接用英文的詞，就用英文，不要硬翻：commit、PR、issue、rollback、build、deploy、log、trace、process、timeout、healthy 這類。句子裡夾英文術語是常態，硬翻成中文反而像機翻，也可能跟專案自己的用詞撞在一起（例如這個專案的「行程」是行事曆上的行程，不能拿來翻 process）。

要翻的時候用台灣的說法，避開中國用語：

| 不用 | 用 |
|---|---|
| 項目（指專案） | 專案 |
| 默認、配置 | 預設、設定 |
| 支持、創建、運行、獲取 | 支援、建立、執行、取得 |
| 數據庫、服務器、接口、文檔 | 資料庫、伺服器、介面、文件 |
| 對象（指物件、目標） | 物件、項目 |

README 的段落標題用中文專案常見的說法，不要從英文直譯：「快速開始」「使用方式」「專案結構」「使用技術」，不寫「怎麼跑」（How to run）；「目錄」在中文 README 指的是內容目錄，講資料夾時用「專案結構」。

## 句子

- 先講結論。一段講一件事。
- 理由只寫讀的人猜不到的，而且只寫一處，其他地方連過去；表格、說明也一樣。放哪一處見 `comments.md` 的「一個理由放一個地方」。
- 一句一個意思，一句最多一組括號。
- 讀的人缺的前提要補上。例如類別名稱裡有 local，可是這個 repo 平常講 local 是指本機，就要說清楚這裡的 local 指什麼。
- 行話和縮寫換成一般說法，例如「接線」寫成「接上 Spring Security」。
- 類別、設定、檔案的名字照原樣放進 `code`，不翻成白話。
- 這些寫法一份文件出現一兩次就太多了：
  - 假對比：「不是 A，而是 B」「不只…更…」
  - 鋪墊：「下面拆成三張圖」「接下來說明」，直接講內容
  - 硬湊三項、四字詞排比：「穩定可靠、高效便捷」
  - 破折號當萬用連接：能用冒號、逗號、句號就不用「——」，標題也不用
  - 「進行＋動詞」：「進行檢查」寫成「檢查」
  - 一長串「的」：「團隊的新的使用者的回饋」
  - 空泛的詞：「至關重要」「全面」「確保」「相關」「唯一」
  - 粗體當裝飾：一份文件最多兩三處，留給做錯會出事的地方
- 例外只寫真的遇過的。
- 三項以內寫成一句；要對照兩欄以上才用表格。issue、PR 的欄位例外，照 `issue.md`、`pr.md` 用條列。
- 不寫開場白和結尾套話（「本文介紹…」「總結來說」「希望對你有幫助」），也不要第一句重複標題。

## 不帶進對話的語氣

文字是在對話裡寫出來的，讀的人沒看過那段對話：

- 「一定要」「刻意」「注意」只留給讀的人真的會做錯的地方，不拿來加強對話裡被交代的事。
- 「不再 X」「改成 A，不用 B」：讀的人只看現在的內容想得到 X、B 才寫；想不到的話，那是在回應對話或舊版本。
- 不寫「照要求」「依照討論」這類交代來源的話。

## 文件放哪裡

- 只跟一個資料夾有關的，放那個資料夾：退版只動 `cd/` 的腳本，說明就是 `cd/rollback.md`。
- 跨好幾個資料夾的放 `docs/`，例如 SLO、告警、架構圖；成套的也放 `docs/`：`adr/`、`runbooks/`、`postmortems/`、`drills/`。
- 一份文件只由它所在資料夾的 README 列進索引，其他文件在句子裡連過去：`docs/README.md` 只列 `docs/` 底下的文件。
- runbook 例外：事故當下不要叫人跳頁，指令可以每份都寫。
- 外部匯出的原檔例外：從別的工具匯出、不是這個專案寫的檔案（例如畫面設計稿），就算只對應一個資料夾，也放 `docs/design/`。放進程式的資料夾的話，build context 要另外排除它；HTML 原型這種帶程式碼的，CodeQL 也要排除。

## 改寫舊文字時

- 意思不能變：條件、否定、範圍、時間、「還沒做」「計畫中」這些狀態都要留著，「可能」不能改成「會」。
- 不加原文沒有的事實、數字、來源。
- 程式碼、指令、路徑、連結、YAML、表格裡的資料原樣保留。
- 改標題前先查有沒有人連到它的錨點（`git grep '#標題'`），有就一起改。
- PR、issue 裡的證據（時間軸、截圖、數字）不刪，只改敘述。
